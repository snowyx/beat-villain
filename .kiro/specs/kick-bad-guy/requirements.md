# 需求文档 · 赛博打小人（Cyber Beat the Villain）

> 参赛作品：InfoQ × 亚马逊云科技「Kiro 鬼点子计划」
> 本文档为 Kiro Spec 驱动开发的第一份产出物（requirements），作为参赛材料之一。
> 权威设计依据：`1-kickbadguy/00-思路与决策.md`（已确认「全按推荐方案」，配音采用 B 方案）。

## 概述（Summary）

赛博打小人是一款把粤港澳民间习俗「打小人」数字化的 **H5 竖屏多人解压仪式应用**。苦主（创建房间的人）开坛立牌、为纸人起花名、选罪状；通过房间码/二维码邀请「神婆」远程进房代打；双方在开打前选择三语咒语（普通话/粤语/英语）并播放开打令；抄鞋抽打至 8 鞋后小人化灰（祥云消散）、撒赛博纸钱、全屏飘「晦气退散」；最后自动生成一张可分享的赛博符咒转运签。任意一方落鞋通过 WebSocket 实时同步给房间内所有人。

定位为「民俗文化体验与解压娱乐」，严格遵守合规红线：不诅咒真人、无血腥暴力、明确标注为粤港澳民间习俗。

### 已确认的技术形态（锁定）

- **形态**：H5 竖屏单页（按微信小程序骨相设计：375px 竖屏、底部 tab 感、分享卡片），可部署为在线链接。不做真·微信小程序。
- **多人协作**：WebSocket 双角色实时房（苦主 + 神婆），房间码 + 邀请链接 + 二维码邀请，房间状态存后端内存。
- **配音（B 方案）**：运行时用浏览器内置 Web Speech API（`window.speechSynthesis`）朗读三语咒语作为占位发声；同时提供一个 ElevenLabs 预生成脚本（Node，从环境变量 `ELEVENLABS_API_KEY` 读 key，批量生成三语咒语 mp3 到 `assets/audio/`），本次不实际调用。前端策略：`assets/audio/` 下存在对应 mp3 则优先播放 mp3，否则回退 Web Speech API。任何 API key 绝不写入代码或提交。
- **部署**：前端纯静态；后端为轻量 Node WebSocket 房间服务（`ws` 库，单文件，内存存房间状态，无数据库）。
- **视觉**：港式霓虹纸扎风，朱砂红 × 鎏金黄 × 霓虹紫，港式招牌楷体感。

### 角色定义

- **苦主（Victim-owner）**：创建房间的人。负责开坛立牌、起花名、选罪状、发起邀请；也可亲自落鞋。
- **神婆（Shaman）**：通过房间码/链接/二维码进房的人，代苦主落鞋开打。
- 两个角色均可落鞋，落鞋结果对房间内所有人实时同步。

## 功能需求（Functional Requirements）

采用 EARS 风格用户故事 + 验收标准。咒语文案直接引用 `00-思路与决策.md` 的表格内容。

---

### 需求 1：开坛立牌（创建房间）

**用户故事：** 作为苦主，我想创建一个「打小人」房间并为纸人起花名、选罪状，以便开坛供奉并邀请神婆代打。

#### 验收标准

1.1. WHEN 苦主打开应用首页并点击「开坛立牌/创建房间」，THE SYSTEM SHALL 进入开坛表单，要求输入纸人花名并选择至少一个罪状标签。
1.2. THE SYSTEM SHALL 提供以下固定罪状标签供多选：抢功劳、甩锅侠、阴阳怪气、已读不回、画饼大师、卷王本卷。
1.3. WHEN 苦主在花名输入框输入疑似真实姓名格式的内容（见需求 11 的拦截规则），THE SYSTEM SHALL 阻止提交，并以提示文案引导其填写「花名/代号」。
1.4. IF 花名为空 OR 未选择任何罪状标签，THEN THE SYSTEM SHALL 禁用「开坛」提交按钮并提示缺失项。
1.5. WHEN 苦主提交合法的开坛表单，THE SYSTEM SHALL 通过 WebSocket 向后端房间服务请求创建房间，并在成功后生成唯一房间码。
1.6. WHEN 房间创建成功，THE SYSTEM SHALL 在后端内存中保存房间初始状态（房间码、花名、罪状标签列表、落鞋计数=0、小人状态=嚣张、咒语语言未定、成员列表含苦主）。
1.7. WHEN 房间创建成功，THE SYSTEM SHALL 将苦主标记为该房间的「苦主」角色并跳转到请神婆（邀请）界面。

### 需求 2：请神婆（邀请进房）

**用户故事：** 作为苦主，我想生成房间码、邀请链接与二维码，以便神婆扫码或点链接进房代打。

#### 验收标准

2.1. WHEN 房间创建成功，THE SYSTEM SHALL 展示房间码、可复制的邀请链接，以及由邀请链接生成的二维码。
2.2. WHEN 苦主点击「复制邀请链接」，THE SYSTEM SHALL 将邀请链接写入剪贴板并给出复制成功反馈。
2.3. WHEN 神婆通过邀请链接或二维码打开应用，THE SYSTEM SHALL 自动带入房间码并进入「进房」确认界面。
2.4. WHEN 神婆输入/带入有效房间码并确认进房，THE SYSTEM SHALL 通过 WebSocket 加入该房间，被标记为「神婆」角色，并接收当前房间完整状态（花名、罪状、落鞋计数、小人状态、咒语语言）。
2.5. IF 神婆输入的房间码不存在 OR 对应房间已关闭，THEN THE SYSTEM SHALL 提示「房间不存在或已散场」并停留在进房界面。
2.6. WHEN 任一成员进房或离房，THE SYSTEM SHALL 向房间内所有成员同步更新后的成员/在线状态。
2.7. IF 房间内成员数达到上限（苦主 + 神婆，MVP 上限为 2 个落鞋角色），THEN THE SYSTEM SHALL 拒绝新的落鞋角色加入并提示房间已满。

### 需求 3：三语念咒（选咒语 + 播放开打令）

**用户故事：** 作为房间成员，我想在开打前选择咒语语言并听到开打令被念出，以便营造仪式感。

#### 验收标准

3.1. WHEN 进入念咒界面，THE SYSTEM SHALL 提供三种咒语语言供选择：普通话（zh-CN）、粤语（zh-HK）、英语（en-US）。
3.2. THE SYSTEM SHALL 使用以下引用自 `00-思路与决策.md` 的三语咒语文案（开打令节选）：
   - 粤语：`打你个小人头，等你有气冇得抖！打你个小人脚，等你日日着错鞋！`
   - 普通话：`一打小人退散，二打晦气全消，三打贵人上门，打完红包拿来！`
   - 英语：`Smack the villain's head, bad luck be gone! Smack the villain's toe, promotions roll on!`
3.3. WHEN 任一成员选择或切换咒语语言，THE SYSTEM SHALL 通过 WebSocket 将所选语言同步到房间内所有成员，使全房共用同一咒语语言。
3.4. WHEN 成员点击「念咒/开打令」，THE SYSTEM SHALL 按配音策略发声：IF `assets/audio/` 下存在当前语言对应的 mp3，THEN 优先播放该 mp3；ELSE 回退使用 Web Speech API（`window.speechSynthesis`）以对应语言（zh-CN/zh-HK/en-US）朗读咒语文案。
3.5. IF 浏览器不支持 Web Speech API 且对应 mp3 不存在，THEN THE SYSTEM SHALL 以文字形式展示咒语文案并给出「当前环境不支持语音朗读」的降级提示，不阻断后续开打流程。
3.6. WHEN 念咒播放完成或成员点击「开打」，THE SYSTEM SHALL 进入开打界面。

---

### 需求 4：抄鞋开打（抽打交互 + 物理与表情反馈）

**用户故事：** 作为房间成员，我想点击/滑动抄鞋抽打屏幕中央的小人，看到它弹跳、表情渐崩并计数，以便获得解压快感。

#### 验收标准

4.1. WHEN 进入开打界面，THE SYSTEM SHALL 将卡通纸片小人展示在屏幕中央，并显示当前落鞋计数与剩余鞋数（目标 8 鞋）。
4.2. WHEN 成员在小人区域点击或滑动，THE SYSTEM SHALL 判定为一次「抄鞋」落鞋，使落鞋计数 +1（即「小人 −1」语义的计数递增）。
4.3. WHEN 发生一次落鞋，THE SYSTEM SHALL 触发纸人物理弹跳动画并播放打击音效。
4.4. THE SYSTEM SHALL 随落鞋进度呈现小人表情渐变的四个阶段：嚣张 → 懵逼 → 冒烟 → 化灰，表情阶段随落鞋计数占 8 鞋的比例推进。
4.5. WHEN 任一成员落鞋，THE SYSTEM SHALL 通过 WebSocket 将「落鞋 +1」事件同步到房间内所有成员；所有成员屏幕的落鞋计数、小人表情阶段、弹跳/震动反馈保持一致。
4.6. THE SYSTEM SHALL 以后端房间内存中的落鞋计数为权威值，前端据此渲染，避免双方同时落鞋导致计数不一致。
4.7. IF 一名成员在开打过程中断线重连，THEN THE SYSTEM SHALL 在其重连后以后端权威状态刷新其落鞋计数与小人状态。

---

### 需求 5：化灰仪式

**用户故事：** 作为房间成员，我想在打满 8 鞋时看到小人化灰、撒赛博纸钱、全屏飘「晦气退散」，以便完成仪式高潮。

#### 验收标准

5.1. WHEN 后端权威落鞋计数达到 8，THE SYSTEM SHALL 判定小人进入「化灰」终态并通过 WebSocket 向房间内所有成员广播化灰事件。
5.2. WHEN 收到化灰事件，THE SYSTEM SHALL 在所有成员屏幕以祥云消散方式表现小人化灰，并撒下赛博纸钱动画。
5.3. WHEN 化灰动画触发，THE SYSTEM SHALL 在全屏飘出「晦气退散」文案。
5.4. THE SYSTEM SHALL 保证化灰表现不出现任何伤口、红色液体或血腥暴力元素（见需求 12）。
5.5. WHEN 小人进入化灰终态后，THE SYSTEM SHALL 停止接受继续落鞋的计数递增，并自动进入转运签流程（见需求 6）。

---

### 需求 6：转运签（生成可分享符咒图）

**用户故事：** 作为房间成员，我想在打完后拿到一张转运签文并生成可分享的赛博符咒图片，以便发给朋友整活传播。

#### 验收标准

6.1. WHEN 化灰仪式完成，THE SYSTEM SHALL 自动抽取并展示一条转运签文，格式包含「宜 / 忌 / 贵人」三项（示例：宜摸鱼、忌背锅、贵人：隔壁组老王）。
6.2. THE SYSTEM SHALL 通过 WebSocket 将本局抽取的签文同步到房间内所有成员，使全房看到一致的签文。
6.3. WHEN 签文展示，THE SYSTEM SHALL 使用 canvas 生成一张符合港式霓虹纸扎风的赛博符咒分享图片，图片内含花名（花名经需求 11 拦截后为非真实姓名）、罪状、落鞋数与签文。
6.4. WHEN 生成分享图完成，THE SYSTEM SHALL 提供「保存图片/分享」入口，供成员下载或分享该符咒图。
6.5. THE SYSTEM SHALL 在分享图或页面可见处保留「民俗数字化体验」标注（见需求 13），确保分享出去的内容仍带合规声明。

### 需求 7：WebSocket 房间实时同步

**用户故事：** 作为房间内的任一成员，我想任何一方的操作都实时反映到所有人的屏幕上，以便双人代打体验一致。

#### 验收标准

7.1. THE SYSTEM SHALL 由后端轻量 Node WebSocket 服务（`ws` 库，单文件，内存存储，无数据库）维护所有房间状态。
7.2. THE SYSTEM SHALL 对每个房间在内存中维护以下权威状态：房间码、花名、罪状标签、咒语语言、落鞋计数、小人状态阶段、是否已化灰、签文、成员及其角色。
7.3. WHEN 任一成员触发以下事件之一——落鞋、切换咒语语言、化灰、生成签文、成员进出房，THE SYSTEM SHALL 更新房间内存状态并向房间内所有成员广播最新状态。
7.4. WHEN 一个成员新进房，THE SYSTEM SHALL 向其单独下发当前房间完整快照以对齐状态。
7.5. IF 某成员 WebSocket 连接断开，THEN THE SYSTEM SHALL 将其从在线成员中移除并向其余成员同步成员变化，房间状态在内存中保留以支持其重连。
7.6. IF 房间内无任何在线成员，THEN THE SYSTEM SHALL 可回收该房间内存状态（MVP 允许在连接全部断开后清理房间）。

### 需求 8：配音（B 方案：Web Speech 占位 + ElevenLabs 预生成脚本）

**用户故事：** 作为开发者，我想在 MVP 运行时用浏览器内置语音占位发声，同时准备好 ElevenLabs 预生成脚本，以便后续可无缝升级为高质量配音且不泄露 key。

#### 验收标准

8.1. THE SYSTEM SHALL 在前端实现配音回退策略：优先播放 `assets/audio/` 下对应语言的 mp3，缺失时回退 Web Speech API 朗读。
8.2. THE SYSTEM SHALL 提供一个 Node 预生成脚本，从环境变量 `ELEVENLABS_API_KEY` 读取密钥，将三语咒语文案批量生成为 mp3 并输出到 `assets/audio/`。
8.3. THE SYSTEM SHALL 在本次交付中不实际调用 ElevenLabs API；脚本作为可运行但默认不执行的工具存在。
8.4. THE SYSTEM SHALL 不在任何源代码、配置文件或提交内容中包含真实 API key；脚本仅从环境变量读取。
8.5. IF 运行预生成脚本时环境变量 `ELEVENLABS_API_KEY` 未设置，THEN 脚本 SHALL 报错并提示用户先设置环境变量，而不写入任何占位 key。
8.6. THE SYSTEM SHALL 使用三语咒语音频文件的可预期命名（如 `spell-zh-CN.mp3`、`spell-zh-HK.mp3`、`spell-en-US.mp3`），使前端回退策略可据文件存在性判断。

### 需求 9：H5 竖屏小程序骨相界面

**用户故事：** 作为移动端用户，我想在手机浏览器打开即玩、布局像微信小程序，以便获得熟悉顺滑的体验。

#### 验收标准

9.1. THE SYSTEM SHALL 以 375px 竖屏为设计基准，页面在移动端浏览器竖屏自适应展示。
9.2. THE SYSTEM SHALL 采用小程序骨相布局：竖屏单页、底部 tab 感的导航区、可分享卡片样式。
9.3. THE SYSTEM SHALL 以港式霓虹纸扎风呈现：朱砂红 × 鎏金黄 × 霓虹紫配色、港式招牌楷体感字体风格。
9.4. THE SYSTEM SHALL 作为纯静态前端交付，可部署为在线链接，用户打开链接即可进入开坛流程。

### 需求 10：部署形态

**用户故事：** 作为参赛者，我想前端纯静态、后端为单文件轻量服务，以便快速部署成可演示的在线链接。

#### 验收标准

10.1. THE SYSTEM SHALL 将前端交付为纯静态资源（可托管于任意静态托管/OSS）。
10.2. THE SYSTEM SHALL 将后端交付为单文件 Node WebSocket 房间服务，依赖 `ws` 库，房间状态存内存，不引入数据库。
10.3. THE SYSTEM SHALL 允许前端通过可配置的 WebSocket 地址连接房间服务，以适配本地与线上部署。

### 需求 11：合规红线 — 不诅咒真人（花名拦截）

**用户故事：** 作为合规负责人，我想花名输入框拦截真实姓名格式，以确保应用不指向真实个人。

#### 验收标准

11.1. WHEN 苦主在花名输入框输入内容，THE SYSTEM SHALL 对疑似真实姓名格式进行校验，至少拦截：2–4 个汉字的常见中文姓名格式、「姓+先生/女士/总/老师」等称谓组合。
11.2. IF 输入被判定为疑似真实姓名，THEN THE SYSTEM SHALL 阻止提交并显示引导文案（例如「请填花名/代号，别打真人~」）。
11.3. THE SYSTEM SHALL 鼓励使用花名/代号（如「卷王本卷」「隔壁组某人」），并可提供花名示例或一键随机花名。
11.4. THE SYSTEM SHALL 在页脚注明「本应用为民俗文化体验与解压娱乐」。

---

### 需求 12：合规红线 — 无血腥暴力

**用户故事：** 作为合规负责人，我想全程无血腥暴力元素，以确保内容健康可过审。

#### 验收标准

12.1. THE SYSTEM SHALL 仅以卡通纸片人形象呈现小人，不使用写实人物形象。
12.2. THE SYSTEM SHALL 在化灰及所有打击反馈中，不出现伤口、红色液体或任何血腥/暴力视觉元素。
12.3. THE SYSTEM SHALL 以「祥云消散」作为小人消失的唯一表现方式。

---

### 需求 13：合规红线 — 民俗定位标注

**用户故事：** 作为合规负责人，我想明确标注「打小人」为粤港澳民间习俗并定位为民俗数字化体验，以确保文化呈现得当。

#### 验收标准

13.1. THE SYSTEM SHALL 在应用内可见处标注「打小人」为粤港澳民间习俗（可注明惊蛰日鹅颈桥下最盛的背景）。
13.2. THE SYSTEM SHALL 将应用定位标注为「民俗数字化体验」。
13.3. THE SYSTEM SHALL 确保音频内容不包含任何真实个人信息。

## 非功能需求（Non-Functional Requirements）

- **实时性**：落鞋等事件的房间同步应为近实时（感知无明显延迟），以保证双人代打的一致体验。
- **一致性**：以后端内存状态为单一事实源（single source of truth），前端渲染不得超越后端权威计数；并发落鞋以后端累加为准。
- **安全与密钥**：任何环境中都不得将 `ELEVENLABS_API_KEY` 硬编码或提交入库；仅通过环境变量读取。
- **可降级性**：音频在 mp3 缺失或浏览器不支持语音时应优雅降级为文字展示，不阻断主流程。
- **可移植性**：前端 WebSocket 地址可配置，后端单文件可在任意 Node 环境/容器运行。
- **轻量**：后端无数据库、无持久化，房间状态仅存内存，符合 MVP 范围。

## 验收标准汇总（关键可测项）

1. 苦主能创建房间、起花名、选罪状，疑似真名被拦截。
2. 神婆能通过房间码/链接/二维码进房，并拿到一致的房间状态。
3. 三语咒语可选、可同步，念咒按「mp3 优先、Web Speech 回退、文字兜底」发声。
4. 点击/滑动落鞋触发弹跳 + 音效 + 表情渐变，计数以后端为准，双端一致。
5. 打满 8 鞋触发化灰（祥云消散，无血腥）、赛博纸钱、「晦气退散」全屏飘字。
6. 自动出「宜/忌/贵人」签文并用 canvas 生成可分享符咒图，带合规标注。
7. 任意一方的落鞋/切咒语/化灰/签文/进出房事件通过 WebSocket 同步到全房。
8. ElevenLabs 预生成脚本从环境变量读 key、本次不实际调用、不泄露 key。
9. 前端纯静态 + 单文件 Node `ws` 后端（内存存储，无数据库）可部署为在线链接。
10. 花名拦截、无血腥、民俗定位标注三条合规红线均在产品中体现。

- 真·微信小程序上架（注册、类目审核、ICP 备案）。

- 围观群众弹幕、递法器（人字拖→高跟鞋伤害加成）等 P1 玩法。
- 本次不实际消费 ElevenLabs 额度，不预生成真实 mp3（前端运行时以 Web Speech 占位）。

## 假设与说明（Assumptions）

- 房间落鞋角色上限为 2（苦主 + 神婆），与「双角色实时房」决策一致；围观属 P1，不在本次。
- 「小人 −1」在设计文档中为打击语义文案，实现上以「落鞋计数递增至 8」作为权威进度表达，两者语义等价。
- 签文的「宜/忌/贵人」条目从一组预置文案中随机抽取，具体文案清单在 design 阶段确定。
- 真实姓名拦截为启发式格式校验（无法 100% 判定真实姓名），目标是合规引导而非严格鉴别；边界规则在 design 阶段细化。
- 二维码在前端生成（静态前端内引入轻量二维码库或等价方案），具体库在 design 阶段确定。
